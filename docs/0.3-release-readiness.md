## 3. Version decision

**Recommend 0.3.0. Choose Strategy B: skip the unpublished 0.2.3 and prepare current `main` directly as 0.3.0.**

The runtime additions since the intended 0.2.3 commit are limited: the public API inventory now states the intended contract, PEP 561 types are shipped, extraction wrapper routing preserves prior behavior, and calibration fails more explicitly if an internal invariant is broken. No caller needs a source change for the proposed release. Still, 0.3.0 is a useful and defensible pre-1.0 milestone because the package adds a complete typed public surface and explicitly describes the expected roles of all 32 exports, including compatibility and experimental boundaries. This makes a new consumer-facing contract available alongside the types. The change is additive; 0.3.0 does not imply that any existing export is removed or warned on.

### Strategy comparison

| Strategy | Advantages | Costs and risks | Assessment |
| --- | --- | --- | --- |
| **A — Publish historical 0.2.3, then later 0.3.0** | Fills the numeric gap and releases the overflow fix separately. | Requires a release from a superseded commit, a second full release cycle soon after, and an intermediate package without the new typing/API contract. More release and changelog overhead for a state that was never public. | Do not choose. |
| **B — Skip 0.2.3 and release current `main` as 0.3.0** | One clear release includes the overflow fix, PEP 561 support, and the documented API contract. A missing patch number is understandable because it was never tagged or published. | Leaves a deliberate PyPI version gap; the changelog must not imply that 0.2.3 shipped independently. | **Recommend.** |
| **C — Skip 0.2.3 and release current work as 0.2.4** | Compatible with a conservative patch-level interpretation because the API remains source-compatible and typing is additive. | Undersells the new typed contract and the API-tier milestone already prepared for 0.3.0; requires retitling the API design record without a stronger compatibility benefit. | Defensible, but less clear than B. |

The release could technically be versioned as 0.2.4 without a SemVer violation. Strategy B is preferred for the explicit API/typing milestone, not because a documentation title alone dictates a version. There is no value in publishing the old 0.2.3 commit first: PyPI continuity does not require every patch number, and that artifact was never available to users.

## 4. API and compatibility audit

The inventory in [public-api.md](public-api.md) contains the same 32 names as runtime `__all__`; there are no missing or extra names. The proposed counts match the inventory:

| Tier | Count | Release disposition |

| Experimental | 2 | Keep unchanged and explicitly out of normal recommendations. |
| Compatibility | 2 | Keep unchanged without warnings. |
| Internal candidate | 1 | Keep unchanged for 0.3.0; reassess later with fresh use evidence. |

### Compatibility exports

- `HighPerformanceStreamingJsonParser` remains the same class object as `StreamingJsonParser`. New code should use the canonical name; preserving the alias and identity avoids unnecessary breakage.
- `__version__` remains the conventional core package version export.
- Do not add warnings or removal plans for either in this release. Their current state is not a blocker.

### Internal candidate: `extract_tuned_complete_json_paths`

This one-shot wrapper preserves its current signature and byte coercion, delegates to `extract_complete_json_paths`, and accepts but does not inspect the optional `sample`. The documented replacement is `extract_complete_json_paths` for one call or `make_tuned_json_path_extractor(..., framing="single")` for a reused workload. The repository usage audit shows no package-internal calls, one test file, and one benchmark script; public GitHub code search found no references outside this repository. That is not proof of no external callers. Keeping the compatibility wrapper unchanged is proportionate: there is no distinct one-shot tuning behavior, but no usage evidence justifies warning or removal in 0.3.0. The inventory’s later-review plan can remain advisory.

### Experimental native exports

`extract_ndjson_paths_native` and `make_ndjson_path_extractor_native` remain Experimental and are described as backend-forcing test/benchmark hooks. Normal docs recommend the generic APIs. Their presence does not require a native release alongside core 0.3.0.

## 10. Release workflow and findings

The core workflow uses GitHub’s published-release event, checks out the event ref (the release tag), runs Python tests, builds the package, checks it with Twine, and publishes through the PyPI action with OIDC (`id-token: write`). The `Build and Publish` PR gate covers typing, lint, coverage, all supported Python tests, native build/tests, and artifact checks. These prerequisites are sufficient when the release tag is created from a green `main` commit.

The core workflow does **not** compare the release tag with `project.version` and `__version__`. Add a small pre-publish parity check or make it an explicit release checklist gate; use `v0.3.0` for the core release and verify both metadata values are `0.3.0`. No release should be created from the assessment branch. The native workflow is separate and already checks its `native-vX.Y.Z` tag against artifact metadata.
