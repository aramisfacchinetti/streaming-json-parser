## 3. Version decision

**Recommend core 0.3.0 next.** The release sequence through 0.2.3 has already happened; there is no remaining decision about whether to publish 0.2.3. The former recommendation to omit that release is withdrawn.

The changes after published 0.2.3 add PEP 561 typing, a type-complete public surface, explicit contracts and tiers for all 32 exports, stable canonical recommendations, cross-platform benchmark-report output, and stronger quality/repository checks. They form a useful pre-1.0 API milestone: users gain machine-readable type information and a clear account of which APIs are primary, advanced, experimental, compatibility-only, or candidates for later review. These changes do not introduce a breaking runtime change or require caller source changes.

### Compatibility exports

- `HighPerformanceStreamingJsonParser` remains the same class object as `StreamingJsonParser`. New code should use the canonical name; preserving the alias and identity avoids unnecessary breakage.
- `__version__` remains the conventional core package version export.
- Do not add warnings or removal plans for either in this release. Their current state is not a blocker.

### Internal candidate: `extract_tuned_complete_json_paths`

This one-shot wrapper preserves its current signature and byte coercion, delegates to `extract_complete_json_paths`, and accepts but does not inspect the optional `sample`. The documented replacement is `extract_complete_json_paths` for one call or `make_tuned_json_path_extractor(..., framing="single")` for a reused workload. The repository usage audit shows no package-internal calls, one test file, and one benchmark script; public GitHub code search found no references outside this repository. That is not proof of no external callers. Keeping the compatibility wrapper unchanged is proportionate: there is no distinct one-shot tuning behavior, but no usage evidence justifies warning or removal in 0.3.0. The inventory’s later-review plan can remain advisory.

### Experimental native exports

`extract_ndjson_paths_native` and `make_ndjson_path_extractor_native` remain Experimental and are described as backend-forcing test/benchmark hooks. Normal docs recommend the generic APIs. Their presence does not require a native release alongside core 0.3.0.

## 10. Release workflow and findings

The core workflow uses GitHub's published-release event, checks out the event ref (the release tag), runs Python tests, builds the package, checks it with Twine, and publishes through the PyPI action with OIDC (`id-token: write`). The `Build and Publish` PR gate covers typing, lint, coverage, all supported Python tests, native build/tests, and artifact checks. These prerequisites are sufficient when the release tag is created from a green `main` commit.

The core workflow does **not** compare the release tag with `project.version` and `__version__`. Add a pre-publish parity check so `v0.3.0` cannot publish artifacts whose core package metadata differs from `0.3.0`. The native workflow already validates its `native-vX.Y.Z` tag against wheel and sdist metadata; reuse that pattern where appropriate. No release should be created from the assessment branch.
